This is a local **Fintech Fraud Operations & Automated Investigation Dashboard** (running on Streamlit at `localhost:8501`).

It is designed to detect, score, and investigate suspicious financial transactions in real time using a combination of a machine learning classifier and an LLM-based investigative agent.

Here is a breakdown of what each part is doing:

### 1. Left Sidebar: Controls & Simulator

* **System Configuration:**
* **Operational Decision Threshold (0.38):** The cutoff score above which a transaction is marked as fraud. Any score $\ge 0.38$ triggers an alert.
* **Champion Model (`fraud-xgb-v1`):** An XGBoost model trained with SMOTE (Synthetic Minority Over-sampling Technique) to handle class imbalance in fraud data.
* **Agent Framework:** Uses a Groq-hosted LLM (`llama-3.3-70b-versatile`) with tool-calling capabilities and a deterministic fallback rule system.


* **Transaction Simulator:**
* A testing sandbox to inject mock transactions (e.g., ID `TX_SIM_7521`, amount `$2450.00`, high 5-minute velocity, rapid geo-distance jumps).
* The simulated transaction scored **0.999** (well above 0.38), immediately setting `Flagged: True`.



---

### 2. Header Metrics (KPI Banner)

* **Registered Champion:** Confirms model version and its performance metric (**PR-AUC: 0.9868**).
* **Flagged Queue Count (7):** Seven suspicious transactions are currently waiting in SQLite storage for review or automated triage.
* **Agent Faithfulness Rate (100.00%):** A guardrail metric ensuring the Groq LLM agent cites real transaction data rather than hallucinating reasons during investigations.
* **Avg Investigator Latency (6.0 ms):** The processing speed for automated triage/inference.

---

### 3. Main Console & Navigation Tabs

* **Live Flagged Transactions (Audit Log Queue):** The active tab showing an audit trail of detected high-risk events (IDs, timestamps, and fraud probabilities hovering around 0.994–0.999).
* **Other Functional Tabs:**
* **Agent Forensic Dossier:** Contains the LLM agent’s narrative reasoning, extracted evidence, and audit write-ups for flagged IDs.
* **SHAP Interpretability:** Feature-attribution charts explaining which factors (e.g., geo-jump, velocity, deviation) drove the score.
* **Model Fairness & Disparate Impact:** Monitors demographic parity/fairness metrics across protected user attributes.
* **Drift Monitoring:** Tracks feature and concept drift over time to detect when the model needs retraining.




The **Transaction Simulator** lets you inject synthetic transaction data to test how the ML model scores the transaction and whether it triggers an alert.

Here is what each field represents:

* **Transaction ID (`TX_SIM_7521`):** A unique identifier assigned to the specific event for indexing, deduplication, and logging in the SQLite audit queue.
* **Customer Profile (`CUST_0042`):** The identifier linking the transaction to an account's baseline history (e.g., standard spending habits, typical location, trusted devices).
* **Merchant ID (`MERCH_002 (Digital Goods)`):** Identifies the merchant and merchant category code (MCC). Certain categories—like digital goods, gift cards, or crypto—natively carry higher chargeback and fraud risk.
* **Amount ($) (`2450.00`):** The monetary value of the attempted charge.
* **Velocity (5 min) (`4`):** The number of transactions attempted by this account or card within the previous 5-minute window. Rapid-fire transactions often indicate automated card testing or account takeover (ATO).
* **Geo Distance Jump (km) (`680.00`):** The physical distance between this transaction’s IP/terminal location and the customer’s previous transaction. A large jump within a short timeframe indicates "impossible travel" (e.g., a card physically used 680 km away within minutes).
* **Amount Deviation (std) (`4.50`):** A $z$-score showing how many standard deviations this purchase amount is from the customer’s historical average. A value of $4.50$ means the charge is an extreme statistical outlier compared to their typical spending.

#### 1. The Inline "Hot Path" (Strict < 50–100 ms SLA)

When you swipe your card or click "Pay", the authorization cycle has a strict latency budget:

* **Hard Rule Engines:** Deterministic rules run first to block hard violations immediately (e.g., country embargoes, stolen card blocklists, exceeded daily limits).
* **Low-Latency Feature Stores:** Systems like Redis compute rolling window aggregations in sub-millisecond time (e.g., "count of card swipes in the last 60 seconds", "distinct IPs in 1 hour").
* **Device Fingerprinting & Biometrics:** Telemetry from the mobile app or browser (keystroke dynamics, device ID spoofing, proxy/VPN detection, canvas fingerprinting).
* **Real-Time Step-Up Decisions:** The scoring engine decides whether to **Approve**, **Decline**, or trigger an **Intervention/Challenge** (e.g., SMS OTP, biometric facial scan, 3D Secure).

#### 2. The Asynchronous "Warm/Cold Path" (Post-Transaction Investigation)

LLMs are generally too slow and costly to sit directly in the sub-50ms inline authorization path. Instead, they run asynchronously:

* **Graph Neural Networks (GNNs):** Run periodically across neo4j/graph databases to discover mule rings, shared synthetic identities, and connected accounts laundering funds.
* **Alert Triage (The Dashboard you see):** When a transaction is flagged or held, this console allows L1/L2 fraud analysts—assisted by LLM agents—to read an automatic evidence dossier, examine SHAP plots, and file a formal SAR (Suspicious Activity Report) to financial regulators.

## The 5 Pipeline Layers (What to Build)

### 1. Ingestion & Streaming (The "Hot Path")

* **What happens:** The user swipes a card or sends money. An event payload lands on an **Apache Kafka** cluster.
* **Stateful Stream Processing:** Use **Apache Flink** or **Kafka Streams** to calculate real-time rolling metrics that the ML model depends on:
* *Rolling windows:* Count of transactions in the last 10 seconds, 1 minute, and 1 hour.
* *Velocity & Geo:* Calculate distance between the current transaction IP and the previous transaction IP stored in memory.


* **Feature Store:** Sync these live aggregations into a high-performance cache like **Redis** (via **Feast** or Tecton) so lookup latency is $< 2\text{ ms}$.

### 2. Dual-Engine Scoring (Rules + ML)

* **Deterministic Rules (Hard Checks):** A fast Java/Go rule engine checks for sanctioned countries, compromised card ranges, or daily regulatory transfer limits before running machine learning.
* **Low-Latency ML Inference:**
* Convert your trained **XGBoost/LightGBM** model to **ONNX format** or serve it with **Triton Inference Server**.
* Inference execution budget: $\le 10\text{ ms}$ per call.


* **Inline Decision:**
* If $\text{Score} < 0.38$: Emit an `APPROVE` payload back to the payment gateway.
* If $\text{Score} \ge 0.38$: Emit a `DECLINE` or trigger `STEP_UP_AUTH` (OTP/Biometric verification).



### 3. Asynchronous Alerting & Entity Graphs

Transactions scoring $\ge 0.38$ are published to an asynchronous Kafka topic (`fraud-alerts-queue`) to decouple investigation from payment routing:

* **Graph Engine (Neo4j / PyG):** Run community detection (e.g., Louvain or PageRank) on the customer ID, IP subnet, device fingerprint, and beneficiary bank account. This catches **money mule rings** sharing the same device ID or virtual card pool.

### 4. LLM Forensic Agent & Automated SAR (Your Dashboard Slice)

* **Agentic RAG:** An orchestrator (e.g., LangGraph) activates for high-severity alerts.
* **Tool Calling:** The agent calls your SQLite/PostgreSQL store, retrieves the user's historical 90-day spending patterns, pulls the SHAP local feature importance values, and checks the Graph database for shared devices.
* **Automated SAR (Suspicious Activity Report):** Formats a regulatory write-up summarizing:
1. *Anomaly profile:* "$2,450 spent on Digital Goods, 4.5 std deviations above norm."
2. *Velocity indicators:* "4 transactions in 5 minutes with a 680 km geo-jump."
3. *Recommendation:* "Block card, notify customer via push notification."



### 5. Continuous Monitoring & MLOps

* **Drift Detection:** Monitor feature drift (Population Stability Index / Wasserstein Distance) between online transaction traffic and the model's offline training distribution.
* **Fairness & Disparate Impact:** Track whether false-positive declines disproportionately penalize specific user cohorts or merchant categories.
